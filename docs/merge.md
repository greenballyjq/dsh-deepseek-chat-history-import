# 合并、去重与版本取舍

多个导出一起导入时，插件按对话 id 合并，而不是简单拼接。

## 1. 什么算同一段对话

只看 **对话 id**：

- 官方导出：`id`
- 浏览器记录：`data.chat_session.id`

标题相同、文件名相同、大小相同、内容相似但 id 不同，都**不算**同一段；不同 id 全部保留。

## 2. 同一 id 的多份，取哪份

先比较**聊天内容**（不看格式、不看消息 id）：

- 角色、消息时间、用户文字、思考、回复文字
- 忽略引用标记（`[reference:N]`、`[citation:N]`、`【N†…】`）
- 忽略空消息、纯工具消息
- 标题不参与内容比较，单独处理

规则：

1. 内容相同 → 保留先读到的一份，不计更新、不计冲突。
   - 如果另一份标题不同：按 `updated_at` → 导出日期采纳较新的标题，仍不计更新/冲突。
2. 内容不同：
   - `updated_at` 较新的胜
   - 时间相同：来源优先级（官方 > 浏览器记录）
   - 再相同：有可信导出日期（ZIP 文件名里的 `YYYY-MM-DD`）取较晚的
   - 再相同：消息更多、更完整的一份
   - 仍分不出：标记**无法判断**，保留先读到的一份
3. **不会把两个版本的消息拼在一起。** 整段取一份。

如果某个来源没有日期（例如解压后的 `conversations.json`、浏览器记录），日期这一步会被跳过，界面会注明“有来源没有日期，未按日期比较”。

## 3. 只在一份里出现的对话

默认**全部保留（并集）**：

- 只出现在较早的导出：保留，面板标「只出现在较早导出」
- 只出现在较新的导出：保留，面板标「只出现在较新导出」
- 两边都出现：按第 2 节取一份

理由：导出文件没有删除标记，无法可靠区分“被删了”和“这份文件没包含”；静默丢数据比多留一段更难发现。只想看当前状态时，只选最新那份即可。

「较早/较新」标签只在**所有来源都是带日期的官方 ZIP** 时显示；混合来源、JSON、单文件不猜新旧。

## 4. 计数

面板按“对话个数”和“出现次数”分别显示：

- **唯一对话**：合并后的 id 数
- **出现在多个来源里的对话**：至少出现两次的 id 数
- **内容相同 / 采用较新 / 无法判断**：上一条里三种结果的个数（三者相加等于“出现在多个来源里”的对话数）
- **出现次数**：同一 id 第二次及以后出现的总次数（只用于统计，不展示为对话数）
- **跳过**：无法识别、损坏、缺失的文件或条目，附原因

两个完全相同的文件：唯一数等于一份，重复出现次数等于另一份的对话数，内容相同数等于该数，更新 0。

## 5. 典型例子

### 两个内容完全相同的 ZIP

- 唯一：N
- 出现在多个来源里：N
- 内容相同：N、采用较新：0、无法判断：0
- 较早/较新独有：0

### 10 月快照 + 11 月快照

11 月删了 2 段、改了 3 段、新增 5 段，10 月有 2018 段：

- 唯一：2018 + 5 = 2023
- 出现在多个来源里：2016
- 采用较新：3；内容相同：2013
- 只出现在较早导出：2（被删的，保留）
- 只出现在较新导出：5

### 解压后的旧 `conversations.json` + 新 v3 ZIP

旧文件没有日期，日期比较会跳过。内容相同的对话保留先读到的一份，不会因为“格式不同”被当成更新；只有真正改过的对话才会计入“采用较新”。

### 同名不同内容

文件名不参与判断，按 id 合并。

### 同一文件里同 id 出现两次

同样按第 2 节处理，计入出现次数。

## 6. 限制

- 这是**合并策略**，不是官方账单或官方删除记录
- “更多消息”是启发式，不保证一定更新
- “无法判断”时保留第一份，是为了确定性
- 不按标题、文件名、内容相似度合并
- 不拼接两个版本的消息
